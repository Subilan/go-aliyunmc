# Pending Permissions

以下权限点需要结合业务数据、任务参数或对象归属判断，单纯依赖路由级中间件（`mid.Perm`）无法完整表达。

## 1. 任务对象级访问控制

- 范围：`GET /task/:id`、`GET /task/:id/output`
- 现状：只要通过路由权限即可读取任意任务详情、订阅任意任务输出。
- 风险：普通用户可能读取其他用户任务的敏感信息（参数、输出、错误细节）。
- 建议：
  - 基本规则：仅允许任务创建者（`task.By == currentUser.ID`）访问。
  - 特权例外：operator/superuser 可访问所有任务。

## 2. 任务触发的参数级权限

- 范围：`POST /task/trigger`
- 现状：路由级只判断“是否允许触发任务接口”，实际细粒度由任务层实现。
- 已有实现：`create_instance` 在使用自定义参数时会检查 `create-custom-instance:execute`。
- 待完善方向：
  - 若后续为 deploy/backup/archive/start_server 增加高风险参数，应在各自 `TaskEnforcerFunc` 中增加参数级授权。

## 3. 资源状态相关的操作授权

- 范围：如删除实例、停止服务端等高风险动作。
- 现状：已通过路由角色做了第一层限制。
- 待完善方向：
  - 可考虑增加“状态门禁 + 角色门禁”双重校验（例如仅在特定状态可删、且需 operator）。
  - 若将来引入多租户/多项目，需要把资源归属纳入授权判断。

## 4. DEV 模式下的权限旁路风险评估

- 范围：`mid.Auth` 在 DEV 模式会注入固定 superuser。
- 现状：便于本地开发，但与生产权限行为不一致。
- 建议：
  - 在文档中明确 DEV 环境属于权限旁路模式。
  - 必要时增加开关，支持在 DEV 中关闭自动 superuser 注入，进行真实权限联调。
